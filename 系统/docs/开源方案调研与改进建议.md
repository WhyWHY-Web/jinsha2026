# 开源方案调研与项目改进建议

> 调研时间：2026-11-16 ｜ 来源：GitHub REST API 实时校验（star / license / 最近提交）
> 筛选原则：**能落进现有三层架构（批处理 → 零依赖服务端 → Three.js 前端）**，不为了用而用。
> 凡是会把 `server.py` 变成"必须 pip install 才能启动"的方案，一律只放批处理层或直接否决。

---

## 一、先看约束：现有架构决定了什么能接

| 层 | 现状 | 可承受的依赖 |
|---|---|---|
| `tools/*.py` 批处理 | 已用 numpy / PIL / subprocess，联网抓 DEM、影像、NASA POWER | **任意重依赖**（离线跑完把结果落盘） |
| `server.py` 运行时 | 纯 Python 标准库，单文件，随 exe 分发 | **不能加任何第三方包** |
| `web/app.html` 前端 | 单页 + Three.js r158（本地 vendor）+ 原生 JS | 可加同源 JS，不宜引入构建链 |

这条约束把候选方案分成两类：**"能进 tools/ 的"** 和 **"只能看不能用的"**。

---

## 二、按优先级排列的改进项

### P0-1 ｜补齐时间维度与退化趋势（对应老师"后期再定制时间维度"）

| 项 | 内容 |
|---|---|
| **针对问题** | 现有"退化风险"是静态估算（覆盖度 + 干燥指数），没有时间序列，无法回答"在变好还是变差"；README 已把"接入 Sentinel-2 时序 NDVI"列为下一步但未做 |
| **推荐方案** | [`google/earthengine-api`](https://github.com/google/earthengine-api)（3.5k★, Apache-2.0）+ [`gee-community/geemap`](https://github.com/gee-community/geemap)（4.1k★, MIT）+ [`davemlz/eemont`](https://github.com/davemlz/eemont)（456★, MIT） |
| **预期效果** | 20 站 × 2000–2025 的 NDVI/EVI/降水/气温月序列，Sen+MK 趋势，退化从"估算"变"趋势判断"；数据血缘可自证 |
| **兼容性** | ★★★★★ 完全落在 `tools/`，产物是 JSON；已在本次改动中落地 `tools/gee_sync.py` + `遥感月值/年值/趋势` 四张表 + `/api/rs/*` |
| **实施方向** | 注册 GEE 非商业 Cloud 项目 → 服务账号存 `tools/gee-key.json` → `python tools/gee_sync.py --start 2015`；再把 `_m()` 里的 `deg` 换成趋势项 |
| **替代/补充** | [`mmhs013/pyMannKendall`](https://github.com/mmhs013/pyMannKendall)（293★, MIT）——若不想自己写 MK 检验，可直接用；本项目的实现已与库内「气候趋势」表同口径 |
| **参考教程** | 你发的 [GEARS（geospatialecology.com）](https://www.geospatialecology.com/) 对应仓库 [`geospatialeco/GEARS`](https://github.com/geospatialeco/GEARS)（84★）与 [`GEE_tutorials`](https://github.com/geospatialeco/GEE_tutorials)；其中 **EMM Lab 6「Monitoring vegetation condition in GEE」** 讲的正是"基准期 vs 近期、累积 EVI 异常"——与本项目退化趋势的口径可以直接对齐 |

### P0-2 ｜把"生态服务"从经验权重换成可复算模型

| 项 | 内容 |
|---|---|
| **针对问题** | `_m()` 里生境质量、水源涵养、土壤保持、碳储量全是经验线性加权（README 也承认"权重为专家经验取值，未做一致性检验"），答辩时最容易被问"凭什么是这个系数" |
| **推荐方案** | [`natcap/invest`](https://github.com/natcap/invest)（259★, Apache-2.0，2026-11 仍在更新）——InVEST 的 Carbon / Annual Water Yield / SDR / Habitat Quality 四个模型正好对应现有 8 维里的 4 维 |
| **预期效果** | 同一套 LULC + 生物物理参数表，输出可复现的碳储量、产水量、泥沙输移比、生境质量栅格；站点值改为栅格采样，公式可写进论文 |
| **兼容性** | ★★★★☆ 纯离线批处理（`tools/invest_run.py`），输出 GeoTIFF → 采样成 JSON，前端零改动；需要准备 LULC 栅格（现有 Sentinel-2 产品可导出）与生物物理表（InVEST 自带模板） |
| **实施方向** | 先用 1 个子流域跑通 Carbon 模型（只需 LULC + 碳密度表，最省事），再扩到 Water Yield（需降水、蒸散、土壤深度、PAWC） |

### P0-3 ｜补"森林景观格局"这一维指标

| 项 | 内容 |
|---|---|
| **针对问题** | 现有 7 个指标全是"数量/占比"，缺"空间格局"——森林破碎化程度是生态评估的常规项，也是评委常问的点 |
| **推荐方案** | [`martibosch/pylandstats`](https://github.com/martibosch/pylandstats)（114★, GPL-3.0）——直接算斑块数、边缘密度、聚集度、香农多样性等 landscape metrics |
| **预期效果** | 每站（或每个子流域）新增 4–6 个格局指数，可与覆盖率组成"数量 + 结构"双维度；雷达图第 9 维 |
| **兼容性** | ★★★★★ 纯离线、输入就是现有 LULC 栅格；输出 JSON 挂到 `eco_item()` |
| **注意** | GPL-3.0：若将来要商业分发 exe，需替换为自实现或 BSD 许可的同类实现（指标算法本身是公开公式） |

### P0-4 ｜水系与地形水文再提升

| 项 | 内容 |
|---|---|
| **针对问题** | 现有河网是自实现 D8 汇流（README："365 条折线"），无 HAND、无子流域边界，陡坡区的"顺谷吸附"仍是启发式 |
| **推荐方案** | [`pysheds/pysheds`](https://github.com/pysheds/pysheds)（920★, GPL-3.0）或 [`jblindsay/whitebox-tools`](https://github.com/jblindsay/whitebox-tools)（1.2k★, MIT） |
| **预期效果** | 标准 D8/D∞、洼地填充、HAND（淹没深度）、子流域划分，替代手工调参；HAND 可直接支撑"洪水淹没"专题层的物理含义 |
| **兼容性** | ★★★★☆ 只在 `tools/build_data.py` 里替换算法，输出仍是 `streams.json`；WhiteboxTools 是独立二进制，无 Python 依赖，最适合本项目 |

### P1-1 ｜形变监测从"演示数据"变成真实 InSAR

| 项 | 内容 |
|---|---|
| **针对问题** | `DEFORM_PTS` 是 12 个硬编码点位（rates 手填），README 明确写"仅保留接口"；这是当前**最容易被质疑真实性**的一页 |
| **推荐方案** | [`insarlab/MintPy`](https://github.com/insarlab/MintPy)（847★）做 SBAS 时序；产线化用 [`yumorishita/LiCSBAS`](https://github.com/yumorishita/LiCSBAS)（288★, GPL-3.0，基于 COMET-LiCSAR 现成干涉图） |
| **预期效果** | 库岸边坡 mm/年 量级真实形变速率，与滑坡敏感性做空间叠加，形成"形变 + 易发性"双证据 |
| **兼容性** | ★★★☆☆ 重计算（需 SNAP/ISCE2 + 几十 GB 数据），只在服务器跑一次，结果落 `deform.json`；前端只需把 `DEFORM_PTS` 改为读接口 |
| **实施方向** | 先取 1 个库区（白鹤滩—溪洛渡）2020–2025 的 LiCSAR 帧，LiCSBAS 出速率图，采样到 12 个点位替换硬编码值 |

### P1-2 ｜树冠高度 / 生物量（GEDI）

| 项 | 内容 |
|---|---|
| **针对问题** | 「数据管理」里 "Meta 1 m 树冠高度" 长期"待接入"；碳密度是系数推算 |
| **推荐方案** | [`geospatialeco/gedi_veg_metrics`](https://github.com/geospatialeco/gedi_veg_metrics)（GEARS 实验室）与 [`geospatialeco/GEDI-BDL`](https://github.com/geospatialeco/GEDI-BDL)（GEDI 波形 + 深度集成回归）；GEE 侧直接用 `LARSE/GEDI/GEDI04_A_002` |
| **预期效果** | 25 m 足迹的真实冠层高度与地上生物量，碳储量从"系数"变"观测 + 外推" |
| **兼容性** | ★★★★☆ 已在 `gee_sync.py` 注册 `agbd`；难点是条带稀疏 → 需按年聚合 + 与 Sentinel-2 特征做回归外推（正好用上项目里"未训练"的 RF 接口） |

### P1-3 ｜空间插值升级

| 项 | 内容 |
|---|---|
| **针对问题** | 专题层用 IDW（README 自述"仅表达空间格局"），站点稀疏时会出现"牛眼"伪影 |
| **推荐方案** | [`GeoStat-Framework/PyKrige`](https://github.com/GeoStat-Framework/PyKrige)（869★, BSD-3）——普通克里金 + 变异函数拟合 |

| **兼容性** | ★★★★★ 只在生成专题层时用，产物仍是纹理/JSON；20 站点规模计算量秒级 |

### P1-4 ｜干旱与气候指标

| 项 | 内容 |
|---|---|
| **针对问题** | "干燥指数"= 蒸散/降水，过于简化；缺标准化干旱指数 |
| **推荐方案** | [`monocongo/climate_indices`](https://github.com/monocongo/climate_indices)（466★, BSD-3）算 SPI/SPEI；[`pyet-org/pyet`](https://github.com/pyet-org/pyet)（166★, MIT）算参考蒸散（Penman-Monteith / Hargreaves） |
| **预期效果** | 3/6/12 个月尺度 SPEI，直接对应"干旱胁迫"因子；蒸散从再分析产品换为可解释的公式计算 |
| **兼容性** | ★★★★★ 纯离线批处理，输入就是已有的 `climate.json` 月序列 |

### P2-1 ｜把平台能力暴露成 MCP 工具（智能体的下一步）

| 项 | 内容 |
|---|---|
| **针对问题** | 现在的智能体是"浏览器内 JS 规则引擎 + 白名单工具"，能力锁在前端；换一个客户端（Claude Desktop / WorkBuddy）就无法操作平台 |
| **推荐方案** | [`modelcontextprotocol/python-sdk`](https://github.com/modelcontextprotocol/python-sdk)（24.9k★, MIT）或 [`PrefectHQ/fastmcp`](https://github.com/PrefectHQ/fastmcp)（28.6k★, Apache-2.0） |
| **预期效果** | 把 `/api/regions`、`/api/region/adjust`、`/api/anomalies` 等包成 MCP 工具，任何支持 MCP 的客户端都能"读指标、改数据、查台账"，前后端交互不再依赖页面 |
| **兼容性** | ★★★★☆ 新增一个独立进程（`tools/mcp_server.py`），复用现有 HTTP 接口，`server.py` 不动 |
| **风险** | 写操作必须保留"白名单 + 台账 + 可撤销"三件套，否则等于给外部开了数据库写权限 |

### P2-2 ｜数据目录标准化（STAC）

| 项 | 内容 |
|---|---|
| **针对问题** | 28 条数据源台账是手填表，缺机器可读的资产清单；`build_detail.py` 其实已经在用 STAC（earth-search）但没沉淀 |
| **推荐方案** | [`stac-utils/stac-fastapi`](https://github.com/stac-utils/stac-fastapi)（327★, MIT） |
| **预期效果** | 每个数据集/批次成为 STAC Item，前端「数据管理」可按时间/空间检索，也便于对接外部平台 |
| **兼容性** | ★★★☆☆ 需要一个 FastAPI 侧车；对课程项目属于"锦上添花"，建议排在 P2 末位 |

### P2-3 ｜全流域 30 m 的 LOD（回应 README 的已知边界）

| 项 | 内容 |
|---|---|
| **针对问题** | README 明确写："整流域无差别 30 m 需要四叉树 LOD 流式加载（约 7 亿格网），尚未实现" |
| **推荐方案** | Cesium quantized-mesh 地形切片（[`CesiumGS/3d-tiles`](https://github.com/CesiumGS/3d-tiles) 规范；生成端 `py3dtiles`，主仓在 GitLab） |
| **预期效果** | 真正无限缩放的流域地形，取代"全域 742 m + 39 块实景补丁"的双轨方案 |
| **兼容性** | ★★☆☆☆ 要换渲染栈或自写 quantized-mesh 加载器，工作量以周计；当前 Three.js 方案在集显上已 60 FPS，**不建议在月底前动** |

## 三、明确不建议引入（避免踩坑）

| 方案 | 为什么不用 |
|---|---|
| LangChain / LlamaIndex | 现有"规则路由 + LLM 只出计划 + 白名单执行"已经够用且可控；引入框架会增加不确定性，工具调用反而更难审计 |
| Superset / Metabase | 数据量只有几千行、图表已在页面内自绘；多一个 BI 服务只增加部署负担 |
| TerriaJS / deck.gl | 当前 20 站点 + 39 补丁，Three.js 足够；deck.gl 的收益在十万级点要素，本项目没有这个量级 |
| Google Earth Engine 前端直连 | 密钥会暴露在浏览器、CORS 受限、断网即废——必须走批处理（本方案已如此） |
| 用 GEE 替换本地 DEM | 交互式三维需要本地高程常驻显存；GEE 适合"取统计值"，不适合"每帧取地形" |
